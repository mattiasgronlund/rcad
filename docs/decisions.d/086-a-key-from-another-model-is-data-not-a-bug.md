## 86. A key from another model is data, not a bug, recorded 2026-09-10

§84.8's inventory, built. Eleven public doors panicked when the key handed to
them was made by a different model; they refuse now, with
`Error::KeyFromAnotherModel` naming the kind of entity the key was for. §4.1's
table has answered bad caller input with `Err` since the beginning, and which
model a key came from is data this crate did not choose.

The unit is one signature change and about three hundred call sites. What is
worth reading is not the count but the line the change draws: **the same
question is caller input at the door and a broken invariant one step inside it**,
and the two now have two different methods rather than one method and a hope.

### 86.1 Two doors on `slot_in`, and which callers take which

`Key::slot_in` used to be the only way from a key to a slot, and it asserted.
There are two now, generated by the same macro for all seven key types:

- `try_slot_in(model) -> Result<Slot>` — for a key that came from a caller. It
  is what the eleven public doors call, and the only thing that can produce
  `Error::KeyFromAnotherModel`.
- `slot_in(model) -> Slot` — unchanged, still asserts. Every caller of it holds
  a key it took off a view of `model` moments earlier, so a mismatch there is a
  bug in this crate, which is the middle row of §4.1's table.

The split is what keeps the change honest. Making `slot_in` fallible everywhere
would have put a `?` on about thirty-five sites inside the crate that cannot
fail, and a `?` on a branch that cannot be taken is the hedge §4.1's third
paragraph and `CLAUDE.md`'s rule 3 both exist to stop. The other direction —
leaving the public doors panicking and calling it an internal invariant — is
what §84.8 already argued against.

`slot_in` carries an `#[allow(dead_code)]`. The macro writes seven of them and
only four kinds of entity are ever reached by key from inside the crate: a
wire, a shell and a coedge are reached through the face or solid that owns them.

### 86.2 The four `*_at` accessors, and why a slot and not a key

`Model::solid_at`, `face_at`, `edge_at` and `vertex_at` are `pub(crate)` and
take a `*Slot`. They are the inside of the crate's door and they answer no
question about which model the thing came from, because a `*Slot` is
`pub(crate)` and every one of them came out of this model's own arena. The type
takes the question away instead of answering it.

Two of them replaced a round trip that had been there since the arenas were
written: `apart.solid(apart.key_for_solid(slot))` minted a key from a model's
own id and then handed it straight back to that model to be checked against the
id it had just been made from.

Four and not seven, because §13's rule is that a part with no named consumer is
not built. `shell_at`, `wire_at` and `coedge_at` have no caller and are not
there.

### 86.3 `Model::fuse` asks before it does anything

`fuse` reaches its argument and tool keys through `Model::solid`, so it would
have refused a foreign key anyway — somewhere in the middle of
`Scratch::split_both_groups`, on whichever group happened to be baked first.
It asks up front instead, of every key in both lists, before a single line of
work:

```rust
for key in arguments.iter().chain(tools) {
    key.try_slot_in(self.id())?;
}
```

Three reasons, and the third is the one that decided it. It makes the refusal
*total* — a tool key in a group that is never baked is asked about too. It
makes the "Atomic" paragraph in `fuse`'s own doc comment trivially true for this
case rather than true by an argument about where the first read happens. And it
lets everything downstream of it use `slot_in` and say plainly that a mismatch
there is this crate's bug, which is what §86.1's split is for; without the
up-front loop, "the key was already checked" would be a claim resting on which
order `split_both_groups` happens to bake its two groups in.

### 86.4 What the tests check, and the half that is the guard

`crates/rcad-topo/tests/a_key_from_another_model.rs`, five tests. Two models,
each holding one cube as its first solid, so every key in one names a slot the
other has too — which is what makes a stranger's key resolve to something real
rather than to nothing, and is the whole reason this was a wrong answer and not
a crash.

- every one of the seven accessors, with a key of its own kind, refused and
  naming the right entity;
- `place_solid` refused, **and the model byte-identical afterwards** —
  `postcard::to_allocvec` before and after, which is stronger than an entity
  count because a placement composed onto a shell moves no count;
- `fuse` refused and the model byte-identical;
- the three `images_of_*` refused;
- the three `set_*_approximation` refused, and `worst_approximation` unmoved.

**Every one of those asks the same question twice**, once with a stranger's key
and once with the model's own, and the second half is the guard. A build that
refused everything passes the first half of all five and is useless. The
`place_solid` test goes further and asserts the bytes *did* move on the
second call, because "a refused placement wrote nothing" says nothing at all
about a `place_solid` that has stopped writing.

The two tests in `tests/what_only_a_release_build_does.rs` changed from
`#[should_panic]` to reading the refusal. What they guard is unchanged and is
not about panics: both answers come out of a comparison that a zero-sized
`ModelId` makes true whichever models the two ids came from, and a debug build
cannot see that (§83.3, §84.7).

**All of them were shown to fail without the check**, the same way §84.7's two
were: `try_slot_in`'s body replaced by `Ok(self.slot)`, which is what a
zero-sized `ModelId` amounted to. The five here and `model.rs`'s
`a_key_from_one_model_may_not_be_used_on_another` — seven tests — all failed,
and so did both release-arm ones while
`these_tests_are_built_with_the_debug_assertions_off` passed in that same run,
which is what says those two failed for the absent check and not for a build
that had dropped back to the dev profile.

### 86.5 What this does *not* close, and why §66.7's first item is different

§84.8 ended by pairing itself with §66.7's first item — `Assembly::commit`
wanting a scratch model so a fuse can refuse before it writes — and said "both
are the same question". They are not, and building this one is what shows it.

This check needs nowhere to fail earlier. It reads nothing and writes nothing
before it answers, so the pre-write door §66.7 wants was already there and only
the return type was missing. `Assembly::commit`'s check is the opposite shape:
it is a check *of what was just written*, and the earliest it could run is after
a copy of the model exists to write into. One is a signature change, the other
is a copy nobody has measured. §66.7's first item stands open.

Nor does this touch §66.7's second item, whether `place_solid` should roll back
with the inverse isometry when the mutation leaves the solid broken. That panic
is still there and is still the right one by §4.1's amendment: by the time it
fires the movement is composed onto the shells and the call cannot take it back.
The two failures in `place_solid` now answer differently on purpose — `Err`
before the write, panic after it — which is exactly the line §4.1's amendment
draws, showing up in one function.

### 86.6 The `.expect` in the STEP writer is not a relapse

`rcad-step`'s `write` takes a `&Model` and no keys. Every key it resolves came
out of `model.solids()` a few lines earlier, so `KeyFromAnotherModel` is
unreachable there and the two sites say so:
`.expect("every key here came off the model being written")`. That is the same
judgement as §86.1's `slot_in`, made in a crate that has no access to
`slot_in` — the public door is the only door `rcad-step` has, and an `.expect`
on it is how a downstream crate writes the assertion.

The test suites use `.expect("this model made the key")` at every one of their
sites, one wording everywhere, so that a reader learns it once and a `grep`
finds all of them.
